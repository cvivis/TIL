- 데이터를 인터넷으로 전송하기 전에 가능하면 압축하라.
	- 1KB당 압축 10µs 
	- 1mb 네트워크로 전송은 10ms
	  BUT , 1MB를 압축 해서보내기, 그냥 보내기 2가지로 보내는 경우 : 압축시간이 전송시간과 비슷경우는 오히려 손해가 된다.
		- 1/3 압축 가정  : (1024kb * 10µs  = 10.24ms) 압축 비용 + (1mb 전송 10ms / 3  = 3.33ms) = **13.57ms** 
		- 그냥 전송 : **10ms** 
		-  실제 구현에서는 데이터를 잘게 쪼개 "압축하면서 동시에 전송"하는 파이프라이닝이 가능해서, 합계가 단순 덧셈(13.57ms)보다 짧아질 수 있긴하나  -> 수치적으로는 오히려 느려지는 경우 발생 
>  시스템에서 가장 느리거나 비싼 자원(느린 네트워크, 디스크 I/O, 메모리 용량, 대역폭 요금)을 통과하는 바이트 수를, 풍부하고 싼 자원(CPU)을 조금 써서 줄여야 되는경우 고려하자

### API URL : v1/me/ feed? content=Hello& auth_tokin={auth_token} 
- v1 : 버전관리 
- auth_tokin: 매 요청 토큰을 통해 무상태 관리 (세션 사용 X)
	- 실무에서는 header에 bearer를 통해 사용. 
- me 
	- 세션이나 토큰 기반이면 사용자 id 정보가 담겨져있을 텐데 굳이 me로 구분하는 이유는?
		- URL의 가독성화 : 사용자의 피드임을 강조
		- v1/users/1234/feed와 대칭 
		- -> 남의 id 노출은 괜찮은건가? : 그렇기에 ID 자리에 URL용 난독화 ID 따로 관리하기도 한다.
- content = Hello

#### URL 설계 규칙

|규칙|잘못된 예시|올바른 예시|설명|
|---|---|---|---|
|동사 대신 명사 사용|`/getUsers`|`/users`|URL은 리소스를 나타내고, HTTP 메서드는 조작을 나타냄|
|복수형 사용|`/user`|`/users`|복수형 스타일 통일|
|소문자 + 하이픈|`/UserProfiles`|`/user-profiles`|URL은 대소문자 구분|
|계층이 너무 깊은 것 피하기|`/a/b/c/d/e`|`/a/b/c`|최대 3계층|
|필터링은 쿼리 파라미터 사용|`/products/phone/5000`|`/products?cat=phone`|필터 조건은 `?` 파라미터 사용|
#### 버전 관리
- 기존 클라이언트의 서비스 중단 없이 시스템을 안전하게 개선할 수 있다.

| 전략          | 예시                        | 장점               | 단점       |
| ----------- | ------------------------- | ---------------- | -------- |
| **URL 경로**  | `/v1/users`               | **직관적, 캐시**하기 쉬움 | URL이 길어짐 |
| **요청 헤더**   | `Accept: vnd.api.v2+json` | URL이 깔끔함         | 디버깅 불편   |
| **쿼리 파라미터** | `/users?version=2`        | 간단함              | 표준적이지    |

#### 버전 관리 모범 절차
- **하위 호환성 유지**: v1 인터페이스는 최소 6-12개월 유지, 클라이언트에 업그레이드 시간 부여
- **문서 동기화 업데이트**: 각 버전마다 독립적인 API 문서 존재
- **폐지 공지**: v1이 언제 종료되는지 미리 알리고, 마이그레이션 안내
- **사용 현황 모니터링**: v1 호출량을 통계하여 안전하게 서비스를 종료할 수 있는지 확인
# 04. 처리율 제한 장치의 설계 
- 처리율 제한 장리 (rate limiter) :클라이 언트 또는 서 비스 가보내는트래픽의 처리율(rate)을제어하기 위한장치.
1. 사용자는 초당 2회 이상 새 글을 올릴 수 없다.
2. 같은 IP 주소로는 하루에 10개 이상의 계정을 생성할 수 없다.
3. 같은 디바이스로 주당 5회 이상 리워드를 요청할 수 없다.
	   
- DoS공격에 의한 자원 고갈을 방지 가능.
- 비용 절감

## 1단계 - 문제 이해 및 설계 범위 확장
- 여러 알고리즘이 사용될 수 있다.
- 클라이언트 쪽 제한 장치 : UI를 비활성화 하거나 하는등으로 클라이언트 쪽에서의 요청을 막는것
- 서버쪽 제한 장치 : 서버 앞단의 API 게이트웨이나 로드밸런서, 비즈니스 로직 중간에서 요청 제어
	- 이미 서버 앞단에서 요청이 들어온거긴 하기에 앞단에서의 분산이 필요할 수도 있다.
> 보통 curl이나 크롬 개발자 도구 등으로 직접 호출 할 수도 있기 때문에 클라이언트 쪽 제한을 하여도 서버쪽 제한 장치가 필수가 된다.
- 제어 규칙 : IP 주소 , 사용자 ID 등 가능 -> 각 계층별 처리율 제한과 연계하여 고민 가능 
- 시스템 규모 : 스타트업 ~ 대기업
- 분산 환경에서의 여부  (처리 장치 1 개 , 여러 서버에서 처리에 대한 공유)
	- 분산 환경: 여러 서버에서 카운터를 공유할 때 경쟁 조건(Race Condition)을 막기 위해 Redis 같은 중앙 저장소가 필요 
- 제한 장치에 대한 SPOF 
- 사용자 인지 여부

  2. 동기화 : 각 분산 서버들이 처리 상태에 대한 동기화가 필요
### 경쟁조건 해결
- 락 but 시스템 성능을 떨어트림. : 공유 자원에 하나의 스레드만 접근하도록 보장 but 나머지 요청이 대기에 걸려 시스템 성능이 떨어짐 
- 루아(Lua) 스크립트 : Lua 스크립트를 실행하는 동안 다른 모든 요청을 '잠시 대기(Block)' 하여 원자적으로 처리 
- 정렬 집합 in Redis

#### 락과 루아 스크립트 모두 대기?
대기 위치ㅣ:	애플리케이션 서버 (느림)	vs Redis 엔진 내부 (매우 빠름)
네트워크 : 네트워크 통신	락 획득/해제 등 여러 번 발생	vs 단 1번으로 끝

### 동기화 해결
- 고정 세션을 활용해 클라이언트별 항상 같은 처리율 제한 장치로 보내는 것. but 클리이언트 1과 연결된 제한 장치가 터지면 사용 X -> 과확장 X  , 유연 X
: 고정 세션 (Sticky Session) : 로드 밸런서가 특정 사용자의 첫 번째 요청을 처리한 백엔드 서버를 기억하고, 이후의 모든 요청을 동일한 서버로 고정하여 전달하는 라우팅 방식
- Redis 와 같은 별도의 외부 데이터 저장소를 사용하자.

## 4단계 - 마무리
### 추가 고려 사항
1. 경성 또는 연성 처리율 제한
	- 경성 : 규정대로 바로 칼 차단
	- 연성 : 트래픽 급증때 바로 차단하지 않기 위해 100의 제한 이지만 120까지는 허용하도록 고려
2. 다양한 계층에서의 처리율 제한 (OSI 7계층)
	- 사용자 ID, API key 등으로 제한 하는것은 애플리케이션 계층에서 확인가능
	- IP 같은 경우 X-Forwarded-For 등의 헤더 정보를 통해 7계층에서 확인이 가능하나 , 3계층에서 확인이 가능한데 굳이 리소스 낭비일 수 있음. 
3. 클라이언트 측에서는? 
	- 클라이언트 측 캐시: 똑같은 데이터를 서버에 10번 요청하지 말고, 한번 받아온 데이터는 클라이언트 캐시에 저장해 뒀다가 다시 써.
	- 백오프 시간을 두자 : 재요청이 빠르게 반복되는 경우 제한의 의미가 퇴색 -> 재시도 간격을 늘리도록 하게 하자.
